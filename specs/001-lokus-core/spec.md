# Feature Specification: LOKUS Core

**Feature branch**: `001-lokus-core`
**Status**: ready for planning
**Language**: product UI in Bahasa Indonesia (default) or English, chosen by the
reader — see US-8 for what the choice does and does not translate. Code and docs
in English.

## Problem

Multi-branch businesses in Indonesia (retail, F&B, clinics, dealer networks)
own three high-value signals they cannot use:

- Google reviews accumulate unanswered — median first response 9 days, most
  never answered at all.
- Location decisions (open, relocate, close) are made without competitor
  density or catchment data.
- Operating knowledge (SOP, product rules, contracts) is scattered across PDFs
  and chat groups, so branch staff improvise and service becomes inconsistent.

Area managers therefore react late and inconsistently across branches, and the
network loses customers without knowing why.

## Users

- **U1 Area Manager** (primary) — owns 5–15 branches, decides daily actions.
- **U2 Branch Manager** — executes actions, asks policy questions.
- **U3 Head of Operations** — wants network-wide patterns, not anecdotes.
- **U4 EBCO delivery team** — operates LOKUS for several client tenants.

## User stories & acceptance criteria

### US-1 Morning briefing
As U1, I receive a morning briefing listing at most three decisions I must make
today, each with a proposed action.

- **AC-1.1** Briefing is generated by 06:00 local time, every day.
- **AC-1.2** Each item shows evidence count and the source documents it used.
- **AC-1.3** Approving an item creates a ticket with an owner and a due date.
- **AC-1.4** The briefing screen also shows what the agents did overnight as a
  timeline (reviews read, replies sent, documents indexed, tool failures
  retried).

### US-2 Theme detection
As U1, I see which complaint themes are rising, per branch and network-wide, so
I can tell local problems from systemic ones.

- **AC-2.1** Themes are derived from review text, not manual tags.
- **AC-2.2** A theme present in 4+ regions is flagged as systemic.
- **AC-2.3** Theme intensity is shown as a theme × branch matrix with an
  8-week trend per row.

### US-3 Reply drafts
As U2, I get a reply draft for every new review, in our brand voice and
consistent with our SOP.

- **AC-3.1** 1–2 star replies require human approval before sending.
- **AC-3.2** Each draft lists the SOP passages it relied on, with page numbers.
- **AC-3.3** Drafts never promise compensation.
- **AC-3.4** Guardrail results (4 checks) are visible before the send action.

### US-4 Policy answers
As U2, I can ask a policy question in plain Indonesian and get an answer with
the SOP page cited.

- **AC-4.1** If retrieval confidence is below 0.70, the answer is "tidak ada di
  dokumen" plus a logged knowledge gap.
- **AC-4.2** Each cited passage is clickable to the source page.
- **AC-4.3** The number of chunks considered but rejected is shown.

### US-5 Location intelligence
As U3, I get a location score per branch explaining under-performance, and
ranked candidates for the next branch.

- **AC-5.1** Score exposes its four factors (foot traffic, surrounding category
  mix, competitor density, parking/access) and their weights.
- **AC-5.2** Candidates closer than 1.2 km to an existing branch are flagged
  for cannibalisation.
- **AC-5.3** Two candidates can be compared factor by factor, with the agent's
  conclusion for each.

### US-6 Multi-tenant operation
As U4, I operate several client tenants from one deployment.

- **AC-6.1** No cross-tenant data is ever returned.
- **AC-6.2** Per-tenant cost and usage are visible in Admin.
- **AC-6.3** Role (admin / manager / viewer) is shown at tenant selection and
  enforced server-side.

### US-7 Conversational diagnosis
As U1, I can ask "kenapa rating cabang X turun bulan ini?" and get an answer
that combines reviews, SOP, and location context.

- **AC-7.1** The supervisor routes the question to the relevant agents and
  merges their findings into one answer.
- **AC-7.2** The execution trace (step number, tool name, result size, latency)
  is shown with the answer.
- **AC-7.3** The answer offers at least one action (create ticket, open
  reviews, show on map).
- **AC-7.4** Per-answer model cost is displayed.

### US-8 Console language
As U3 and U4, I read the console in English while my branches keep operating in
Indonesian, so the interface language must be my choice and must not change the
language customers and branch staff are addressed in.

The choice governs **the console's own words** — everything LOKUS wrote. It does
not govern **content that belongs to the tenant's world**. Three layers, and the
boundary between them is a product decision, not a shortcut:

| Layer | Follows the locale? | Examples |
|---|---|---|
| Console chrome and static copy | yes | nav, screen titles, buttons, the four data states, table headers |
| Agent-authored copy | yes | briefing timeline and decisions, metric labels, guardrail check explanations, site-scout reasoning, comparison conclusions, refusal reasons, ticket status columns |
| Tenant content | **no** | customer review text, SOP passages and their quotations, the public reply drafted for a review, document titles |

- **AC-8.1** A language control is reachable from every screen and offers exactly
  Indonesian and English. Indonesian is the default for a reader who has never
  chosen.
- **AC-8.2** Choosing a language re-renders the console immediately, persists the
  choice across reloads, and sets `<html lang>` to match.
- **AC-8.3** Numbers and dates follow the chosen locale: `3,04` and
  `30 Juli 2026` in Indonesian, `3.04` and `30 July 2026` in English. No screen
  mixes the two conventions.
- **AC-8.4** Agent-authored copy served by the API follows the locale the console
  requested, and the locale travels on the request rather than being inferred
  server-side.
- **AC-8.5** A reply drafted for a customer review stays in Indonesian whatever
  the console language is, and a cited answer quotes its SOP passage verbatim in
  the language the document is written in. The console may explain such content
  in English; it may not translate it.
- **AC-8.6** Neither dictionary has a key the other lacks, and the check is
  automated rather than reviewed by eye.
- **AC-8.7** A rejected action explains itself in the reader's language when the
  console has copy for the failure, and in Indonesian rather than not at all when
  it does not. No failure renders as an empty panel or as a bare error code.

### US-9 Listing access level
As U4, I can see for every outlet what LOKUS is actually permitted to do with
its Google listing, so an outlet nobody is allowed to reply to is never mistaken
for one that is merely waiting on a click.

Google serves review data through two APIs with different access models, and the
difference is not a configuration detail — it changes what the Reputation agent
can honestly promise for a given branch:

| Level | Condition | Reviews available | Reply |
|---|---|---|---|
| **L0 absent** | the outlet has no listing on Google Maps at all | none | no |
| **L1 public** | a listing exists, but the tenant neither owns nor manages it | the 5 Google chooses to expose, read-only (Places API New) | no |
| **L2 managed** | the listing is claimed and verified, and the managing account has granted LOKUS the `business.manage` scope | full history, paginated (Business Profile API v4) | yes |

Replying is a property of ownership, not of credentials: no API key, quota
increase, or billing change lifts L0 or L1 to a reply. A tenant onboarding at
L0 or L1 is a normal state to be reported, not an error and not a blocker.

- **AC-9.1** Every outlet carries a level, and any screen showing its review
  data shows the level alongside.
- **AC-9.2** The level is derived from what the credentials actually returned on
  the last run, never from a flag set by hand. A revoked grant drops an outlet
  to L1 on the next nightly cycle rather than reporting a stale success.
- **AC-9.3** L1 uses the needs-permission state, which offers a connect action
  because a person can act on it. L0 does not: it says the outlet has no listing
  and offers no connect button, because connecting cannot fix it.
- **AC-9.4** A reply is never offered for an L0 or L1 outlet. A draft written
  for one is stored as unsendable with its reason, rather than failing at the
  moment the send is pressed.
- **AC-9.5** Metrics that assume full review history — median first response,
  share answered within 48h — count only L2 outlets, and every screen reporting
  them states how many outlets were excluded and why.
- **AC-9.6** At L1 the console states that five is Google's ceiling rather than
  the outlet's review count, so a quiet branch and a capped one do not read the
  same.

## Success metrics

| Metric | Baseline | Target |
|---|---|---|
| Median first response time to a review | 9 days | under 8 hours |
| Reviews answered within 48h | 31% | above 90% |
| Rising theme detected before rating drops 0.2 | never | 7–10 days earlier |
| Ticket close time | not measured | under 5 days (SLA) |
| Cost per tenant per month | — | under IDR 5.4M |

## Non-goals

Social-media sentiment, POS integration, staff scheduling, native mobile apps,
real-time streaming ingestion.
